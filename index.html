NeuroIK Documentation

Desktop robot design, analysis, training & deployment

1Overview

NeuroIK is a desktop application for designing a robot arm, understanding how it behaves, and getting it to do something useful. It covers the whole path from a folder of CAD meshes to a trained model on an ESP32 — and every stage in between is a workflow you can use on its own.

1.3 This workflow: teaching a network to solve IK

The rest of this tab is the ML for IK workflow: design a robot, generate a dataset from it, train a model, check the model in a live 3D viewport, and export it for deployment — from an NVIDIA GPU down to an ESP32.

The core idea: FK-first data

Inverse kinematics asks: “which joint angles put the gripper here?” Generating training data by guessing poses would fill the dataset with unreachable targets. NeuroIK inverts the problem:

  1. Your recipe defines each joint's limits.
  2. Random joint values are sampled within those limits.
  3. Forward kinematics computes exactly where the end-effector lands.

Every row is therefore reachable by construction, and the network learns the inverse of a guaranteed-correct mapping. No impossible poses ever enter training.

Note: IK is one-to-many — many joint configurations reach the same pose. NeuroIK trains against a forward-kinematics (task-space) loss, rewarding any joint vector that reaches the target, rather than forcing the network to average conflicting valid answers.

2.2 Install & run

Put the NeuroIK folder anywhere you like and double-click NeuroIK.bat. That is the whole installation.

On the first run it installs everything NeuroIK needs and then opens the app. Every run after that skips straight to opening the app.

Heads-up — first run only: a console window appears while the dependencies download. This is a few GB and takes several minutes; leave it alone until it finishes and the app window appears. Later launches are silent and much faster.
Tip: want an icon on your Desktop? Run python desktop.py --install-shortcut once. Afterwards you can start NeuroIK from the Desktop icon instead of the batch file — no console, just the app.

Closing the app window shuts everything down; nothing keeps running in the background.

Everything the app produces lives under a single data/ folder:

2.4 A portable build

NeuroIK can be packaged into a folder that runs on any Windows machine with no Python installed — copy it to a USB stick and go.

python build_exe.py --venv buildenv\Scripts\python.exe --zip

The result is dist/NeuroIK/; run NeuroIK.exe inside it. Your projects are written to a data/ folder created beside the executable, so the whole folder stays self-contained and moves with your work.

One real trade. The portable build uses the CPU-only PyTorch wheel, because the CUDA one is around 4.5 GB against 200 MB — and needs a matching NVIDIA driver on the target machine anyway. GPU training is therefore unavailable in the portable copy; use the source install for that. TensorFlow and coremltools are also left out, which costs the TF Lite, Keras H5 and Core ML export formats (3 of 10). Everything else — all six workflows, CPU training of every architecture, ONNX and the remaining exports — works.

Full details, including what to do if it will not start, are in docs/PORTABLE-BUILD.md.

3.1 Available robot types

SCARA

Two revolute joints sweep in a horizontal plane, a prismatic Z axis mounted at the elbow provides vertical travel, and an optional 4th revolute wrist spins the tool. IK: closed-form analytical. Parameters: link lengths L1/L2 (m), Z travel range, optional wrist limits.

Delta

Three arms mounted 120° apart drive a floating platform; the robot hangs from its base and reaches below it, so its Z workspace is negative. IK: trilateration. Parameters: exactly four — [R_base, R_platform, L_upper, L_lower].

Note: a Delta is a 3-DOF translation-only machine — orientation is always zero. Those constant pose dimensions are detected and masked during training.

Cartesian

Three prismatic axes map 1:1 onto X/Y/Z, with an optional wrist. IK: direct mapping — no iteration needed. Parameters: travel range per axis.

Articulated

An anthropomorphic chain: a base yaw joint and column, parallel-pitch shoulder and elbow, and — at 6+ DOF — a spherical wrist (roll · pitch · roll) whose axes meet at a single point. DH parameters are generated automatically from your link lengths, and the home pose stands straight up along +Z. IK: numerical damped least-squares with 12 multi-start restarts.

Custom URDF

Instead of describing a robot by hand, import one. Click Custom URDF and enter a path — either the .urdf/.xacro file, or the folder containing it (recommended: mesh references resolve relative to that folder).

NeuroIK walks the real chain and uses each joint's true origin (xyz + rpy) and axis, so imported robots run on a dedicated exact-kinematics engine — not the auto-generated DH approximation used by the generic Articulated type. That exactness is what lets your CAD line up with the joint motion. IK: numerical damped least-squares with multi-start restarts.

What gets imported
  • Joint count, types and limits — revolute limits convert from radians to degrees; prismatic stays in metres. continuous joints and joints with no <limit> default to ±180° (you'll get a warning).
  • Link lengths — the distance from each actuated joint to the next, with any intervening fixed joints folded in.
  • Visual geometry — rendered in the Live Preview and Simulation.
Mesh formats

STL, DAE and OBJ are rendered, as are URDF <box>/<cylinder>/<sphere> primitives. Paths are resolved through package://, file://, absolute and relative forms — and finally by filename anywhere under the folder, which covers descriptions whose package:// paths don't match the shipped layout.

STEP / IGES are not rendered. They're B-rep CAD formats that need a CAD kernel to tessellate into triangles — a browser can't. Those links show a translucent placeholder; kinematics, datasets and training are unaffected.
Xacro support

.xacro files are expanded internally — no ROS install required: <xacro:property>, ${...} arithmetic, <xacro:include> and <xacro:if>/<xacro:unless>. Expressions are evaluated over a restricted AST, never eval().

<xacro:macro> is not supported. Expanding macros correctly is a large job, and a partial implementation would silently produce a wrong robot. Pre-expand instead: xacro robot.xacro -o robot.urdf, then import the generated robot.urdf.
Branches and mimic joints

The whole tree is drawn, not just the actuated chain — so side branches like a gripper's second finger appear. The DOF, however, come from the longest actuated chain.

A <mimic> joint is driven by another joint, so it is not an independent DOF: it's excluded from the joint count (and from the network's outputs) but follows its source in 3D via value = multiplier × source + offset.

Editing after import

Joint limits and link lengths stay editable — narrowing limits is a legitimate way to shape the dataset, and changing a link length rescales the spacing to the next joint (kinematics and the 3D view stay in step). The DOF count and joint types are locked by the file: the engine rejects a joint count that disagrees with the parsed chain, and flipping a type would corrupt the degrees/metres conversion.

Note: CAD meshes are rigid parts — they keep their own size when you change a link length, so a large change will show a visible gap between links.
Only some of my meshes appear

NeuroIK draws the links the URDF declares. If a folder ships 13 STLs but the description references 7, you'll see 7 — the rest are spare parts no link points at. Add <link>/<joint> entries to use them.

3.2 Recipe Builder

The Recipe Builder is where a robot becomes concrete:

  • Link lengths — each joint's link, in metres.
  • Joint type — revolute (degrees) or prismatic (metres).
  • Joint limits — min/max per joint. These bound the sampling, so they define the reachable workspace.
  • Dataset size — 10K, 100K or 1M samples.
  • Name — saved with the project.

Live Robot Preview

The preview renders through the same code as the Simulation tab, so what you see here is what you'll simulate. It updates as you type — no need to regenerate a dataset first.

  • Joint Controls — one slider per joint, bounded to the limits you set, to pose the arm and sanity-check its reach before committing to a dataset.
  • SCARA J3 — the vertical prismatic travel is derived from the 3rd link length (the quill descends from 0 to −L3), so those limit fields are read-only and follow the link.
  • Imported URDFs are framed automatically, since they arrive at any scale.

Workspace analytics

After generation NeuroIK analyses the reachable volume (x/y/z ranges) and uses it to calibrate the Simulation sliders — so default targets land where the robot can actually go. This is why a Delta's Z slider is negative: it reaches below its base.

Tip: 10K is fine to smoke-test the pipeline. Use 100K+ for a production-quality model. 1M with a complex chain can take several minutes.

5ML Studio

GPU or CPU — chosen automatically

NeuroIK picks the training device at run time: CUDA if a usable GPU is present, CPU otherwise. There is nothing to configure and nothing breaks without a GPU. A banner at the top of ML Studio always states which device the next run will use.

Have an NVIDIA GPU but training is still on the CPU? This catches almost everyone on Windows. PyPI's default torch wheel is CPU-only, so a plain pip install torch gives you a build where torch.cuda.is_available() is permanently False — the GPU is never touched, however capable it is. Check with:

python -c "import torch; print(torch.__version__, torch.cuda.is_available())"

A build ending in +cpu (e.g. 2.2.2+cpu) is the CPU-only wheel. Install the CUDA build instead:

pip install --force-reinstall torch --index-url https://download.pytorch.org/whl/cu121

NeuroIK.bat now does this for you on first install: it looks for nvidia-smi and pulls the CUDA wheel when a GPU is present.

ML Studio detects this exact situation — GPU present, torch unable to use it — by asking the driver via nvidia-smi rather than trusting torch, and shows the fix inline. The /api/system endpoint reports the same thing:

5.1 Architectures

MLP — Multi-Layer Perceptron

Structure: 6 → 256 → 512 → 512 → 256 → 128 → N, GELU activations, LayerNorm, dropout.
Data: 10K–100K  ·  Best for: every robot type, as a fast baseline

  • Pros — fastest to train, lowest memory, excellent on SCARA/Cartesian/Delta. The only architecture that exports to a complete TinyML header.
  • Cons — no built-in mechanism for multi-modal solutions; can plateau on long articulated chains.

Transformer

Structure: encoder over 6 learned token embeddings, multi-head self-attention, LayerNorm, learned positional encoding.
Data: 100K+  ·  Best for: articulated / SCARA with long-range coupling

  • Pros — attention captures dependencies between pose dimensions and joints.
  • Cons — more memory, slower, hungrier for data.

GNN — Graph Neural Network

Structure: message passing over the kinematic chain — joints are nodes, links are edges; 3 rounds of learned node/edge updates.
Data: 50K+  ·  Best for: articulated arms

  • Pros — the network encodes chain topology explicitly.
  • Cons — overkill when the structure is trivial (Cartesian).

Diffusion — DDPM

Structure: denoises random joint vectors conditioned on the target pose; cosine schedule, FiLM conditioning. At inference it samples 16 candidates and keeps whichever FK says lands closest.
Data: 100K+  ·  Best for: poses with several valid solutions

  • Pros — handles multi-modal IK naturally; strongest in ambiguous cases.
  • Cons — ~16× slower inference, heaviest to train.

PINN — Physics-Informed

Structure: MLP backbone plus an FK-consistency loss penalising predictions whose FK misses the target.
Data: 10K–50K  ·  Best for: small datasets

  • Pros — best sample efficiency; physically consistent.
  • Cons — dual objective can be unstable if the FK weight is off.

RL Agent

Structure: actor-critic (PPO-style) with behaviour-cloning pretraining; reward is pose error.
Data: 100K+  ·  Best for: research and experimentation

  • Pros — can discover strategies absent from the data.
  • Cons — needs reward tuning; non-deterministic outputs.

6Simulation Studio

6.1 The 3D viewport

  • Controls — drag to orbit, scroll to zoom, right-drag to pan.
  • Real scale — everything is drawn in metres, matching the recipe.
  • Markers — a green sphere marks the target; a blue sphere marks where the model actually put the end-effector.
  • Collisions — for articulated arms, non-adjacent links are AABB-checked; colliding pairs turn red.
Note on axes: the viewport is Z-up — Z is vertical, matching the engine's convention. The Z slider raises the target; Y moves it in depth.

6.2 Running inference

Set the target with six controls — X/Y/Z in metres, roll/pitch/yaw in degrees — then press Predict & Animate. Each slider has a number box beside it for exact entry; the box is authoritative, so it also accepts values outside the slider's range when you need a target the slider can't reach.

The results panel reports:

The ⓘ icon next to Analytical Joint Values opens the actual IK formulas for the loaded robot — the closed-form SCARA solution, the Delta per-arm trilateration, the Cartesian direct mapping, or the damped-least-squares iteration used for Articulated and imported URDF robots.

"Unreachable / No IK" on a target that looks reachable? The badge reports that the analytical solver found no solution. Check the target is genuinely within reach — a SCARA with L1+L2 = 0.7 m cannot reach 0.82 m, and no solver (neural or classical) can change that. The ML model will still return its closest attempt at the workspace edge.

6.3 Random target

Random Target gives a guaranteed-reachable pose. If the project has a generated dataset it returns an actual row from it — the exact distribution the model was trained on, which is the fairest way to spot-check accuracy. Otherwise it samples random joints within your limits and runs FK. Either way the pose is reachable by construction, so a blind bounding-box guess never lands outside the workspace.

6.4 Export panel

After a successful prediction, the Export Model panel appears beneath the viewport with all ten targets. Hover any ⓘ for a one-line summary of what a format is for, and see §7 for integration code. Formats that cannot represent the current architecture report a clear message instead of exporting — check the support matrix first.

7Exporting Models

Every export reports format_name, file_size_mb, param_count, supported_runtime and validation_passed, and is written to data/exports/<format>/.

7.1 Normalization is baked in

NeuroIK trains on normalized values, but you never have to think about that. Every export folds the normalization constants into the model itself: feed a raw pose in metres and radians, read real joint units — degrees for revolute joints, metres for prismatic — straight back out.

joints = model(pose)          // that's the whole contract

Each export still ships a model_meta.json beside it, both as documentation and so tooling can read the I/O layout:

model_meta.json 
{
  "model_type": "mlp",
  "input_dim": 6,
  "output_dim": 4,
  "pose_order": ["x","y","z","roll","pitch","yaw"],
  "pose_units": "x/y/z in metres, roll/pitch/yaw in radians",
  "joint_units": "degrees for revolute joints, metres for prismatic",
  "normalization": { "x_mean": [...], "x_std": [...],
                      "y_mean": [...], "y_std": [...] },
  "normalization_baked_in": true,
  "usage": "joints = model(pose) - normalization is built into the graph..."
}
Do not apply the constants yourself. They are published for reference only. Applying (pose - x_mean) / x_std before calling a baked model normalizes the input twice and produces confident-looking nonsense. Always check normalization_baked_in — it is true for every format except one.
The single exception: the ROS2 package. Its ik_node.py applies the constants explicitly in predict(), so its model_meta.json reports "normalization_baked_in": false. The node handles it for you; you only need to care if you load best_model.pt yourself.
How it works. Traced formats (ONNX, TorchScript, TensorRT, Core ML) export a thin wrapper module that scales on the way in and out. TF Lite and Keras H5 instead absorb the constants into the first and last Dense layers — an affine op folded into an adjacent affine layer is mathematically identical and costs nothing at inference. TinyML and the native DLL emit the arithmetic directly into their generated C. Every one is verified against PyTorch numerically at export time, so a mis-folded constant fails the export instead of shipping.

7.2 Which formats work with which architecture

Not every architecture can become every format. Formats that rebuild the network layer-by-layer (TF Lite, Keras H5, native DLL) need a plain feed-forward stack; diffusion, GNN, transformer and RL keep their real logic inside forward(), so those combinations are refused at export time rather than silently producing a model that has the right output shape but computes the wrong function.

7.3 ONNX

File: model.onnx + model_meta.json  ·  Opset: 17, dynamic batch  ·  Runtime: ONNX Runtime, OpenVINO  ·  I/O: pose float32[B,6] → joints float32[B,N]

#include <onnxruntime_cxx_api.h>
#include <vector>

Ort::Env env(ORT_LOGGING_LEVEL_WARNING, "neuroik");
Ort::Session session(env, "model.onnx", Ort::SessionOptions{});

float pose[6]     = {0.5f, 0.3f, 0.2f, 0.0f, 0.0f, 0.0f};
int64_t shape[2]  = {1, 6};

auto mem   = Ort::MemoryInfo::CreateCpu(OrtArenaAllocator, OrtMemTypeDefault);
auto input = Ort::Value::CreateTensor<float>(mem, pose, 6, shape, 2);

const char* in_names[]  = {"pose"};
const char* out_names[] = {"joints"};

auto out = session.Run(Ort::RunOptions{nullptr},
                       in_names, &input, 1, out_names, 1);

float* joints = out[0].GetTensorMutableData<float>();
// joints[0..N-1] are already in real units.

Link against onnxruntime. Ort::Value does not own the buffer, so `pose` must outlive the Run() call.

import numpy as np
import onnxruntime as ort

sess = ort.InferenceSession("model.onnx")

# Raw pose: [x, y, z, roll, pitch, yaw] in metres and radians.
# Normalization is inside the graph -- do not apply it yourself.
pose = np.array([[0.5, 0.3, 0.2, 0.0, 0.0, 0.0]], dtype=np.float32)

joints = sess.run(["joints"], {"pose": pose})[0]
print(joints[0])          # degrees (revolute) / metres (prismatic)

# The batch axis is dynamic -- stack rows to solve many poses at once.

7.4 PyTorch

File: model.pt  ·  Runtime: PyTorch 2.0+  ·  Use for: continued training, fine-tuning, research

Note: this is a full checkpoint dictionary (weights + architecture metadata + normalization), not a TorchScript archive — so load it with torch.load, not torch.jit.load. That is what makes it re-trainable.
This is the one format where you apply normalization yourself. A raw checkpoint is the bare network — there is no graph to bake anything into. If you just want to run the model rather than train it, use TorchScript instead, which needs none of this boilerplate. 
import torch
import numpy as np
from backend.ml.models import create_model

ckpt  = torch.load("model.pt", map_location="cpu", weights_only=False)
model = create_model(ckpt["model_type"], ckpt["input_dim"], ckpt["output_dim"])
model.load_state_dict(ckpt["model_state_dict"])
model.eval()

# This is the ONE format where you normalize yourself -- a bare checkpoint has
# no graph to fold the constants into.
x_mean, x_std = np.array(ckpt["x_mean"]), np.array(ckpt["x_std"])
y_mean, y_std = np.array(ckpt["y_mean"]), np.array(ckpt["y_std"])

pose = np.array([[0.5, 0.3, 0.2, 0.0, 0.0, 0.0]])
x = torch.tensor((pose - x_mean) / x_std, dtype=torch.float32)

with torch.no_grad():
    joints = model(x).numpy() * y_std + y_mean

7.5 TorchScript

File: model_torchscript.pt + model_meta.json  ·  Runtime: LibTorch C++, PyTorch 2.0+, TorchServe  ·  Architectures: all six

A TorchScript module is self-contained: it carries its own architecture, so it loads with no model class, no create_model, and no NeuroIK source on the target machine. The module is traced and then torch.jit.freezed, which inlines the weights and folds away the module hierarchy.

This is the full-precision option for C++ robot controllers — no conversion to a foreign framework, so the numbers match PyTorch to within float round-off (validated at export to 1e-5 of a joint standard deviation).

#include <torch/script.h>
#include <iostream>

int main() {
    torch::jit::script::Module model = torch::jit::load("model_torchscript.pt");
    model.eval();

    // Raw pose -- normalization is traced into the module.
    torch::Tensor pose = torch::tensor({{0.5f, 0.3f, 0.2f, 0.0f, 0.0f, 0.0f}});

    torch::NoGradGuard no_grad;
    torch::Tensor joints = model.forward({pose}).toTensor();

    std::cout << joints << std::endl;   // real joint units
}

import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Pose
from sensor_msgs.msg import JointState

class IKNode(Node):
    def __init__(self):
        super().__init__("neuroik_ik")
        self.sub = self.create_subscription(Pose, "target_pose", self.solve, 10)
        self.pub = self.create_publisher(JointState, "joint_command", 10)

    def solve(self, msg):
        pose = [msg.position.x, msg.position.y, msg.position.z, 0.0, 0.0, 0.0]
        joints = self.model_forward(pose)     # generated for you in ik_node.py

        out = JointState()
        out.header.stamp = self.get_clock().now().to_msg()
        out.name     = self.joint_names
        out.position = [float(j) for j in joints]
        self.pub.publish(out)

9Project Management

A project is the unit of work. It stores the robot type, recipe, every generated dataset, every training run with its metrics, and every export — as JSON under data/projects/. Reopening restores all of it, even after a restart.

Choosing which dataset / model to use

A project can hold several datasets and several trained models. The Dashboard has a dropdown for each:

  • Active dataset → used by ML Studio for training and retraining.
  • Active model → used by Simulation for prediction and by Export.

Deleting datasets and models

Each selector has a Delete button that removes the selected dataset or trained model from the project and deletes the app's working copy under data/. If you delete the active one, the next most recent is promoted automatically.

What is never deleted: copies mirrored into your own Project Root Folder, and models you already exported. Those live outside the app's storage — they're yours, so NeuroIK leaves them alone and tells you where the kept copy is.
Deletion is permanent. A deleted dataset can be regenerated from its recipe; a deleted model must be retrained.

10Troubleshooting & FAQ

1. The exported model returns nonsense values

Almost always double normalization. Every export except the ROS2 package now has the constants baked in, so you must feed a raw pose and read real joint units directly. Applying (pose - x_mean) / x_std yourself normalizes the input twice. Check normalization_baked_in in model_meta.json and see §7.1.

If you are loading the raw model.pt checkpoint, the opposite applies — that one is the bare network and does need the constants. Use TorchScript if you just want to run the model.

2. Export fails with “disagrees with PyTorch by …”

Working as intended: every convertible format is checked numerically against PyTorch before it is written, and the export is aborted rather than shipping a model that computes the wrong function. Report the number — it is expressed in units of a joint standard deviation.

3. “Only plain feed-forward models (MLP, PINN) can be converted”

TF Lite, Keras H5 and the native DLL rebuild the network layer by layer, which only works for a plain stack. Diffusion, GNN, transformer and RL keep their logic in forward(). Either train an MLP for those targets or export ONNX/TorchScript instead — see the support matrix.

4. Export succeeds but validation fails

The model's output width must equal the robot's joint count. Check that the active robot matches the one the model was trained on. For Core ML off macOS, and ROS2 when TorchScript tracing is unavailable, validation_passed is reported as false by design — the file is still produced, but the check could not be run here.

5. “No trained model found” when exporting

Train a model first. Export uses the model selected on the Dashboard, falling back to the most recent checkpoint.

6. Accuracy is poor

In order: generate more data (100K+), train longer, confirm the robot config matches training, then try a stronger architecture (Transformer/Diffusion). If you changed the recipe, you must regenerate and retrain.

7. Diffusion inference feels slow

By design — it samples 16 candidates and FK-checks each. For real-time control use MLP or Transformer.

8. TF Lite or Keras H5 export fails

TensorFlow is required for both: pip install tensorflow. Core ML likewise needs pip install coremltools. Every other format works without either.

9. TinyML header has no ik_forward()

You exported a non-MLP model. Only plain feed-forward networks reduce to straight-line C. Train an MLP.

10. The 3D viewport is blank

The viewport uses WebGL. Update your GPU drivers; on a remote/virtual desktop, hardware acceleration may be unavailable.

11. Dataset generation takes too long

1M samples with a complex chain takes several minutes. Use 100K while iterating.

12. "No .urdf or .xacro file found under: <path>"

The folder holds no description file. Point at the folder that actually contains the .urdf/.xacro (subfolders are searched too), or at the file itself. Quoted paths pasted from Explorer's Copy as path are handled.

13. My URDF imported, but a link's mesh is missing

Two likely reasons. Either the mesh is in an unsupported format — only STL, DAE and OBJ render; STEP/IGES show a placeholder — or the URDF never declares that link. NeuroIK draws what the description declares, so spare meshes shipped in the folder but not referenced by any <link> won't appear. The import warnings list both cases.

14. "This file uses <xacro:macro>"

Macro expansion isn't supported — a partial implementation could silently build the wrong robot. Pre-expand with the ROS tool and import the result:

Bash 
xacro robot.xacro -o robot.urdf

15. My imported robot has one DOF fewer than I expected

Probably a <mimic> joint — a gripper's second finger, say. It is mechanically driven by another joint, so it is not an independent DOF and must not be a network output. It still moves in the 3D view, following its source joint.

4“I derived the IK, but I cannot check it”

IK Calculator

The problem. You worked out the closed form on paper. It gives an answer. Is it right? Is it the only answer? A numerical solver converges — but to which of the eight valid configurations, and was the one it picked the one you wanted?

Why it matters. IK is one-to-many. Picking the wrong branch is not a small error — it is the arm swinging through the workpiece to reach the same point from the other side.

What NeuroIK does. Closed-form solvers where the geometry allows one — SCARA with explicit lefty/righty, planar 2R/3R, and a gated Pieper decomposition returning up to eight solutions for a true spherical wrist. Three numerical solvers with multi-start where it does not. Then it shows you the derivation, step by step, with your real numbers substituted into the symbols — not a textbook formula, the actual arithmetic that produced your answer.

5“It reaches. But can it move?”

Jacobian & Singularity Studio

The problem. Reachability is a solved question and it is the wrong one. An arm can place its tool anywhere in its workspace and still be nearly useless at specific points — demanding enormous joint speed for a slow tool motion, in one particular direction.

Why it matters. This is the failure that looks like a mechanical fault. The arm shudders. A joint screams. The servo faults on overspeed. Nothing is broken — you drove it through a singularity, and the geometry told you it was coming if anyone had asked.

What NeuroIK does. Full SVD of the Jacobian at any pose: singular values, rank, condition number, Yoshikawa manipulability, isotropy. A velocity ellipsoid drawn in 3D that flattens into a disc at the exact moment a direction of motion is lost — you do not read that in a number, you watch it happen. Then a singularity map across one joint's full travel, or a heatmap across two, so you can see where the bad regions are before you plan a path through them.

The moment it pays off: drag a slider, watch the ellipsoid go flat, and understand — properly, physically, in one second — why that pose is one to design out.

6“I sized the motors from the holding torque”

Torque & Dynamics Studio

The problem. Almost everyone computes gravity torque, picks a motor with margin, and ships. Gravity is the term that is non-zero standing still — it is also routinely a fraction of what the joint delivers during a real move.

Why it matters. The motor stalls on the bench. The gearbox wears in six months. The arm cannot run the cycle time you promised. And the fix is mechanical, so it costs the whole build.

What NeuroIK does. Recursive Newton-Euler, the full equation — τ = M(q)q̈ + C(q,q̇)q̇ + G(q) + F(q̇) — with every term broken out so you can attribute a torque instead of guessing at it. Feed it a trajectory and get peak, RMS (the thermal question everyone skips), peak power, energy, and the instant the peak occurs. Sweep the whole workspace for the worst-case payload — the figure that belongs on a spec sheet, not the flattering one at the pose you happened to be standing in.

The moment it pays off: it searches for the worst gravity pose by measuring rather than assuming, because the "obvious" straight-out pose is wrong for most engines. It hands you the configuration that actually decides your motor size.

1What Motion & Path Planning does

The ML for IK workflow trains a network to answer one pose at a time. This workflow answers a different question: given a sequence of poses, produce a motion a controller can actually execute — interpolated in Cartesian space, solved into joint space, time-scheduled against velocity and acceleration limits, checked for collisions and singularities, and exported in a format your controller reads.

It does not use a trained model. Every pose along the path is solved with the robot's own exact inverse kinematics. A network is an approximation with an error budget; a taught path is a thing a machine will physically follow, and the two do not belong in the same pipeline. Train a model in ML for IK if you want one — this studio is deliberately independent of it.

The pipeline

  1. Waypoints — poses you teach, in metres and degrees.
  2. Segments — how to get from each waypoint to the next: line, curve, arc or spiral.
  3. Interpolation — the segment is sampled into a dense Cartesian polyline.
  4. IK sweep — every sample is solved into joint values, seeded from its predecessor.
  5. Time scheduling — a trapezoidal or S-curve profile turns geometry into a timed trajectory.
  6. Validation — self-collision, obstacles and singularities, on demand.
  7. Export — CSV, JSON, Epson SPEL+, G-code or a ROS 2 JointTrajectory.

2Teaching waypoints

A waypoint is a full pose: x, y, z in metres and roll, pitch, yaw in degrees. Three ways to create one.

Add point

Type it

Import

2.1 Per-waypoint controls

Selecting a waypoint in the list opens its own panel: pose fields, the segment type used to arrive at it, its blend radius, and its own velocity and acceleration scaling. Waypoints can be reordered, duplicated and deleted, and dragging the coloured arrows in the viewport moves one along its axis.

Reachability is checked as you teach. A waypoint the arm cannot make is marked immediately rather than at plan time, because the fix — move it, or change the robot — is something you want to know while you are still looking at that point.

3Segment types

Each segment says how to travel from the previous waypoint to this one. Interpolation happens in task space, so the tool follows the shape you asked for regardless of what the joints have to do.

3.1 Orientation along a segment

Roll, pitch and yaw are interpolated with shortest-angle wrapping. A path that crosses ±180° therefore takes the short way round instead of spinning the wrist almost a full turn — which is both slower and, on a wrist with a hard stop, impossible.

3.2 Corner blending

A blend radius rounds the corner at a waypoint instead of stopping dead on it. The waypoint is still passed near, not through; set the radius to zero for a corner the tool must hit exactly.

Blending shifts sample indices. Waypoints solved before blending are mapped back onto the blended path, so the exported trajectory still reports where each taught point actually landed rather than where it was before the corner was rounded.

4From geometry to a schedule

The planner produces geometry: an ordered list of joint vectors with no notion of time. A controller needs a schedule — when each configuration should be reached, given how fast each joint may move and how hard it may accelerate. Two profiles are offered.

ProfileAccelerationTrade
TrapezoidalConstant — ramp up, cruise, ramp down The classic industrial profile. Fastest for a given velocity/acceleration pair, but acceleration steps discontinuously, so jerk is unbounded.
S-curveSmoothstep applied to the velocity ramps Bounded jerk. Slightly slower, much gentler on gearboxes — and it is what stops a taught path from visibly shaking a lightweight arm.

Scheduling works on a normalised path parameter s ∈ [0, 1], which keeps the maths independent of the joint count and of whether a given joint is revolute (degrees) or prismatic (metres). Velocity and acceleration limits are set per joint under the motion panel, and a waypoint can scale them down locally for a slow approach.

5Solving the path

Every interpolated sample is solved with the robot's exact IK. Two details make the result usable rather than merely correct.

5.1 Seeded from the previous solution

IK is one-to-many. Solving each sample independently would let the arm flip between elbow-up and elbow-down mid-path — mathematically valid at every point, and a violent reconfiguration in practice. Each solve is therefore seeded from the previous sample's answer, so the chain stays in one branch.

5.2 Unwrapping

A revolute joint at +179° moving to −179° is a 2° move, not a 358° one. Solutions are unwrapped against the previous sample so the exported numbers describe the short move the robot will actually make.

Unreachable samples are reported, not skipped. If a mid-segment point falls outside the workspace the plan says so and names the segment. A path that silently drops points is a path that does something different from what it draws.

6Collision & singularity checking

Check Path runs the expensive validation on demand — it is not run on every edit, because it sweeps the whole dense path.

Self-collision

Links are modelled as capsules of a radius derived from the arm's own scale, and every non-adjacent pair is tested along the path. Adjacent links are excluded — they share a joint and always touch.

Obstacles

Boxes and spheres you place in the scene, tested against the same capsules and against the tool point.

Singularities

Each sample's conditioning is checked against a limit. A path that passes through a singularity is one where joint speeds spike towards infinity even though the tool is moving slowly.

A failing check raises a dialog naming what was hit and where, rather than a silent flag on a list you might not scroll to.

For a deeper look at why a pose is near-singular — which direction of motion is being lost, and by how much — open the same robot in the Jacobian & Singularity Studio.

8What this workflow will not do

  • It will not plan around an obstacle for you. It checks the path you taught. There is no sampling-based planner here — no RRT, no PRM — so a blocked path is reported, not re-routed.
  • It will not choose your velocity limits. Those come from your drives' datasheets. The defaults are placeholders, and a schedule computed from a placeholder is a schedule about a robot you do not own.
  • It does not model dynamics. The profile respects velocity and acceleration limits, not torque limits. Whether your motors can actually deliver that acceleration is the Torque & Dynamics Studio's question, and the two are worth running together before committing a path to hardware.

3Closed-form solvers

A closed form returns every solution at once, exactly, in microseconds — and tells you how many there are, which a numerical solver never can.

3.1 SCARA

Two solutions for a reachable point: elbow-left and elbow-right. The forward kinematics is

T = Rz(θ₁)·Tx(L₁)·Rz(θ₂)·Tz(d₃)·Rz(θ₄)

so x = L₁c₁ + L₂c₁₂, y = L₁s₁ + L₂s₁₂, z = d₃ and yaw = θ₁+θ₂+θ₄. The elbow follows from the law of cosines, the shoulder from a two-argument arctangent, the slide is read straight off z, and the wrist absorbs whatever yaw is left over.

Handedness is selectable. Set the arm to lefty or righty and the whole application follows — the calculator, the path studio and the 3D model. Left on auto, the solver returns both and ranks them.

3.2 Planar 2R and 3R

Standard closed forms, with the reachability test done before the arctangent rather than after — so an unreachable target is reported as unreachable instead of as a NaN.

3.3 Cartesian

Each prismatic axis maps to one coordinate. The inverse is a rename plus a limit check, and it is documented as such rather than dressed up as a derivation.

3.4 Six-DOF with a spherical wrist (Pieper)

When the last three axes intersect at a point, position and orientation decouple: the wrist centre is found by stepping back from the target along the approach vector, the first three joints place it, and the last three take whatever rotation remains. Up to 8 solutions.

Gated, and self-verifying. The decomposition is only offered when the wrist axes really do intersect. Every candidate it produces is then pushed back through forward kinematics and discarded if it does not land on the target. That check is what caught a real bug during development: an incorrect Euler extraction was producing too few solutions, never wrong ones — the wrong ones never got past FK.

Three iterative methods, all built on the same core loop so they differ only in the step they take.

Damped least squaresΔq = Jᵀ(JJᵀ + λ²I)⁻¹ e The default. Stable through singularities — damping trades a little accuracy for a finite step where the pseudoinverse would demand an infinite one.
PseudoinverseΔq = J⁺e The minimum-norm step. Fastest convergence away from singularities, unstable near them.
Newton-RaphsonΔq = J⁻¹e Square Jacobians only. Quadratic convergence when it works.

4.1 Multi-start

Every numerical method restarts from several seeds. A single start finds a local answer; a target with eight valid configurations reached from one seed reports one of them, and gives no hint the other seven exist.

4.2 Convergence is scored on both errors

The best iterate is tracked as

score = max( position_error / position_tolerance ,
             orientation_error / orientation_tolerance )
This is not cosmetic. Scoring on position alone — the obvious first implementation — let a solver hit the position tolerance around iteration 10 while the orientation was still 51° out, then freeze that iterate as "best" for the rest of the run and report it as converged. Both errors are normalised by their own tolerance so neither can hide behind the other.

4.3 Uncontrollable axes are masked, not down-weighted

A SCARA cannot roll or pitch. Asking it to is not a small error to be weighted down — it is a constraint that does not exist. Those rows are removed from the Jacobian entirely and the remaining ones are weighted equally.

7Validation

A solution is only offered after it passes three checks.

  1. Joint limits — every value inside its own travel.
  2. Forward kinematics round-trip — the solution is pushed back through FK and the resulting pose compared against the target.
  3. Distinctness — duplicates that differ only by numerical noise are collapsed, so "4 solutions" means four genuinely different arm configurations.
Reaching the target is not the same as being a good answer. A solution sitting in a near-singular pose, or hard against a joint stop, is a poor thing to command from even when its position error is excellent. The Jacobian studio can rank a set of solutions on exactly that basis.

1What the Jacobian Studio does

Inverse kinematics answers can the arm get there. This studio answers how well can it move once it is there — which directions are easy, which are expensive, and how close the pose is to losing a direction of motion entirely.

The Jacobian J maps joint rates to tool rates:

ẋ = J(q) · q̇

Everything on the page is a property of that matrix at the current configuration. Move a slider and all of it recomputes.

Why this matters in practice. Near a singularity the tool can still be placed anywhere reachable, but moving it in one particular direction demands joint speeds that rise without bound. A path that looks fine geometrically can be impossible dynamically, and this is where that shows up.

2Building the Jacobian

2.1 Two methods

MethodHowMeasured cost
Finite differencesCentral differences on the engine's own FK≈ 0.69 ms
AutogradPyTorch reverse-mode through the differentiable FK≈ 11.6 ms

They agree to about 2 × 10⁻⁸ relative. Finite differences is therefore the default for interactive work and for sweeps: a 25×25 map is 625 Jacobians, which is 0.4 s by differences and 7 s by autograd, for a difference invisible at chart resolution.

This is worth stating because the obvious assumption runs the other way. Autograd is exact to machine precision and finite differences is not — but the gap here is far below anything the metrics resolve, and 17× is the difference between a page that responds to a slider and one that does not.

2.2 Structural rows

A SCARA has no roll or pitch. Keeping those rows would give the matrix two permanently zero rows, and every rank and condition number computed from it would be wrong.

NeuroIK finds the structurally controllable rows by sampling many configurations and taking the union of the rows that are ever non-zero — not by inspecting one pose. A single pose can have an accidentally zero row, and using it would report a permanent structural fact where there was only a momentary one. For a SCARA the result is vx, vy, vz, ωz.

2.3 Units and Euler rates

Columns are normalised per radian (or per metre for a prismatic joint), so a mixed arm's columns are comparable. Where orientation is expressed as Euler rates, the mapping ω = E(rpy)·ṙpy is applied — and gimbal lock in that mapping is flagged separately from a genuine mechanical singularity, because one is an artefact of the representation and the other is a property of the machine.

3The SVD metrics

Everything is derived from one singular value decomposition, J = UΣVᵀ.

MetricDefinitionRead it as
Singular values σDiagonal of Σ The gain along each principal direction. The smallest is the direction the arm is worst at.
RankCount of non-negligible σ How many independent directions the tool can move in right now. Less than full means one has been lost.
Condition number κσ_max / σ_min The headline number. Scale-free, so it is the one to threshold on. 1 is perfectly isotropic; ∞ is singular.
Manipulability w√det(JJᵀ) Yoshikawa's index — the volume of the velocity ellipsoid. Zero exactly at a singularity.
Isotropyσ_min / σ_max κ inverted, bounded in [0, 1]. Convenient for a bar or a colour.
w carries units, κ does not. Manipulability shrinks when you shorten a link and cannot be compared between two robots of different size — halve a SCARA's forearm and w halves with it, as it should. The condition number is a ratio of singular values and is scale-free. Threshold on κ; use w to compare poses of one arm.

4Thresholds and why not det(J)

Four verdicts, from the condition number with a smallest-singular-value backstop.

StatusDefault ruleMeaning
SAFEκ < 30Well conditioned in every direction.
WARNING30 ≤ κ < 100Degraded. One direction is getting expensive.
NEAR_SINGULARITYκ ≥ 100, or σ_min below its floorNearly unusable; joint speeds are climbing steeply.
SINGULARRank deficientA direction of motion is gone.

30 and 100 are the conventional working numbers for serial manipulators. They are editable — a small delta and a long redundant arm genuinely differ — and the thresholds actually applied are returned with every verdict, so a result is never un-reproducible.

Never from the determinant. det(J) exists only for a square Jacobian, so it is undefined for any redundant or under-actuated arm. It is also scale-dependent: a determinant of 10⁻⁶ means "singular" on an arm measured in metres and "perfectly healthy" on the same arm measured in millimetres. The SVD is defined for every shape and the condition number is dimensionless.

5The velocity ellipsoid

The 3D view draws the set of tool velocities produced by a unit sphere of joint speeds. Its axes are the singular vectors and its radii the singular values.

  • Round — the arm moves equally well in every direction.
  • Flattened — the short axis is the direction that is becoming expensive.
  • A disc — that direction is gone; the pose is singular.

This is the same information as κ, in the form where it is obvious which direction is in trouble — a number cannot tell you that, and it is usually the thing you need in order to decide where to move the path.

6Differential kinematics

6.1 Forward — joint rates in, tool velocity out

One matrix product. Always defined.

6.2 Inverse — desired tool velocity in, joint rates out

Near a singularity an exact inverse asks for joint speeds no machine can produce. Four methods:

MethodBehaviour
AutoDamp only when the pose is near singular. The sensible default.
Exact inverseSquare, full-rank Jacobians only.

The tracking error is reported, never hidden. Damping is a trade: you asked for a tool velocity and you are getting a slightly different one in exchange for joint speeds that exist. The studio shows both the joint rates and the velocity you will actually get, plus a warning when the solution drives a joint further into a stop it is already resting on.

7The singularity map

Pick one joint for a curve, two for a heatmap. The remaining joints stay where the sliders leave them.

7.1 One joint — a curve

Manipulability and 1/κ across that joint's full travel, with the exact crossings into trouble listed underneath rather than left to be read off the chart by eye.

A flat curve is drawn flat. Rotating a SCARA's base joint cannot change the arm's internal geometry — rotating a Jacobian leaves det(JJᵀ) unchanged, so manipulability is mathematically invariant to q₁. Auto-scaling would fit the axis to the finite-difference noise floor (about 5 × 10⁻⁹ on a value of 0.085) and draw a dramatic zigzag out of the eighth decimal place. Any series varying by less than a part in a million of its own magnitude is held to a readable span and labelled constant.

7.2 Two joints — a heatmap

Colour is log₁₀ κ, stretched over the range the scan actually covers. Two deliberate choices:

  • Logarithmic, because κ is a ratio: the step from 8 to 16 matters as much as the step from 80 to 160.
  • Fitted to the healthy cells, because singular ones run to infinity and would otherwise own the entire scale. Cells at or past the near-singular threshold are pinned to the dark end and counted in the legend, so nothing is hidden by fitting the scale to the rest.
A linear scale on 1/κ — the obvious first choice — is unreadable in practice. A healthy arm sits at κ ≈ 5–50, so on a real SCARA scan the brightest cell in the whole map reached only 0.117 of a 0–1 ramp and 76% of cells fell below 0.1. Everything came out dark red on a grid of perfectly healthy poses.

Hovering any cell gives its exact joint values, κ, w and σ_min. Legend endpoints are labelled with real condition numbers, not just "singular" and "good".

8Editing the arm in place

Conditioning is a property of the mechanism, so the questions worth asking here are about the mechanism. Three things are editable without leaving the page, and every one of them recomputes the Jacobian, its SVD, the verdict and the 3D model.

DOF

Within the range the robot type allows — SCARA 3–4, Cartesian 3–6, articulated 2–12. Delta is fixed at 3 and an imported URDF is fixed by its parsed chain.

Link lengths

The moment arms that set every entry in the linear rows. Shorten a SCARA's forearm from 0.30 to 0.15 m and manipulability halves — w is linear in link length.

Joint travel

The exact interval the singularity map scans. Narrowing a limit clamps the current pose into it and says so; an inverted range is refused rather than silently swapped.

A derived limit stays derived. A SCARA's vertical slide travels the length of its column, so q₃'s limits follow L₃ and are shown read-only with a from L3 badge rather than pretending to be independently editable.

8.1 Ranking IK solutions

Given a set of candidate solutions — analytical, numerical or ML-predicted — the studio scores each on conditioning and on how much joint travel is left before a stop, and ranks them. This is the cross-check the whole studio exists for: an ML prediction being close to the target says nothing about whether the pose it lands in is a usable one to command from.

1What the Torque & Dynamics Studio does

What each joint actually has to deliver:

2The mass-data gap, stated up front

NeuroIK's robot recipe carries link lengths, joint types and limits. Nothing physical. No robot in this application arrives with the mass, centre of mass and inertia tensor that dynamics needs — and this module will not invent them, because a made-up mass produces a made-up torque and nothing downstream could tell.

So the studio opens with a gate. There are exactly three provenances, and they are never conflated:

3Physical properties

3.1 Robot geometry

DOF and link lengths are editable here, because both change the torques directly — link length is the lever arm gravity acts through. Changing DOF regenerates estimates automatically (they were derived numbers anyway) but never silently reshapes values you typed: the page drops back to the gate and says the properties described a different number of links.

3.2 Total robot mass

If you have put the arm on a scale, type what it weighs. Every link is rescaled by the same factor, which is exactly a uniform change of density — inertia is linear in mass at fixed geometry, so every tensor scales with it and the centres of mass do not move at all.

The total then becomes your figure; how it is distributed between links is still whatever it was. An estimate that put too much mass in the forearm still does. Payload is separate and is not counted in this number.

3.3 Estimating from a primitive

Each link is modelled as a tube running along the offset to the next joint, with its centre of mass at the midpoint of that offset — which is where a uniform link's mass actually sits.

Why a tube and not a solid rod. A real arm link is a shell or an extrusion. Estimating it as solid overstates the mass several-fold and the inertia more. And the COM offset matters more than the shape: a link modelled as a cylinder is centred on its own middle, but the joint is at its end — leaving that offset at zero puts every link's mass on its own axis and produces almost no gravity torque. That is the single most common way to get a plausible-looking but badly wrong result.

3.4 Plausibility checks

Check plausibility tests each link against the physics an inertia tensor must satisfy — positive mass, positive-definite tensor, triangle inequalities on the principal moments — and reports what fails and why.

4How the torques are found

Recursive Newton-Euler, in the Craig frame convention. An outward pass propagates velocity and acceleration from base to tip; an inward pass propagates forces and moments back, and the joint torque falls out as the projection onto each joint's own axis.

QuantityObtained by
Gravity torque G(q)RNEA with q̇ = q̈ = 0
Mass matrix M(q)One RNEA call per column, with a unit acceleration on one joint and gravity off
Coriolis C(q,q̇)q̇RNEA with the real q̇, gravity and q̈ off
Friction F(q̇)Viscous + Coulomb, per joint, from the actuator table

The breakdown sums exactly to the total, so a term can be attributed rather than guessed at. Gravity defaults to the standard 9.80665 m/s² and is editable — including to zero, which is a real use case and produces a genuinely different answer.

4.1 Payload

A payload is combined into the last link by the parallel-axis theorem, at the grip offset you give. Picking something up does not add a degree of freedom, so it is not modelled as one.

5Live torques

Move the joint sliders and the torque breakdown updates. A schematic arm is drawn beside them — six joint angles are hard to picture, and this is the same numbers, drawn.

Per-joint bars show each torque as a share of that joint's own limit where one is entered. With no limit there is nothing to be a fraction of, so the bar falls back to a share of the largest torque in the pose and says so.

5.1 Worst gravity pose

A button searches for the configuration that demands the most torque — the one that decides motor size.

It searches rather than assumes. The obvious shortcut — put every rotary joint at zero, "straight out" — is wrong here and measurably so: NeuroIK's articulated engine gives its shoulder a +90° DH offset, so all-zeros is the vertical candlestick pose where the links stack over the base and the gravity torque is near zero. A hardcoded convention would also differ per engine and rot whenever one changed. Sampling is slower than a formula and always right.

7Payload & motors

7.1 Payload at this pose

What the arm can hold exactly where it is standing. Useful, and on its own misleading.

7.2 Payload across the envelope

The worst case anywhere the arm can reach — the figure that belongs on a spec sheet. A payload search is bisected at every sampled pose, so it takes real time and reports as it goes: a progress bar, a pose counter, elapsed time, an ETA once the rate means anything, and the worst payload found so far converging in front of you.

The running figure can only fall as more poses are tried, which is why it is worth showing: you can stop reading as soon as it drops below what you need.

7.3 Motor advice

Per joint: peak required, continuous required, the gear ratio you entered, both figures referred back to the motor shaft, and a suggested drive class. Gearing is applied where you state it — torque divides and speed multiplies — because a 100:1 reduction is the difference between a plausible motor and an impossible one.

8What this studio will not do

8.1 Friction defaults to zero

With no friction entered, every torque on the page is an ideal-drive lower bound. A real gearbox adds to it, often a substantial fraction of the no-load torque. Size a motor from these figures and it may be undersized. Enter the viscous and Coulomb terms from your drive's datasheet under Actuator limits. The page carries a standing banner while friction is unset — this is not a footnote.

8.2 A delta gets no dynamics at all

Recursive Newton-Euler walks a chain from base to tip. No ordering of a delta's links reproduces its kinematics — its three arms share the platform as a closed loop. Dynamics for a parallel machine needs a different formulation, which this module does not implement.

So it declines, with the reason, rather than producing numbers from a chain that is not this robot. Numbers from the wrong model look exactly like numbers from the right one.

8.3 It is rigid-body dynamics

No link flexibility, no gear backlash, no drive-train compliance, no thermal model beyond the RMS figure. For a stiff industrial arm these are second-order; for a long slender one they are not.

1What the CAD → URDF/Xacro Studio does

The upstream step: where a robot comes from when all you have is meshes. Every other workflow in NeuroIK starts by selecting a robot; this one is how a robot gets created.

It is a generator, not a converter. CAD geometry carries shape and nothing else. An STL knows where the metal is; it does not know where the joints are, which way they turn, what their limits are, or what anything weighs. Those are decisions you make, and this studio is organised around making them — not around uploading a file and hoping.

The four steps

  1. Import — read and measure your geometry.
  2. Links & joints — build the tree, set axes, origins and limits.
  3. Physical properties — mass, centre of mass, inertia.
  4. Generate — URDF or Xacro, validated, ready to export or load.

2.1 Files are read from disk, not uploaded

A 200 MB assembly never travels through the browser. Press Browse… and you get a real OS file dialog in the desktop app, or a built-in folder browser in an ordinary browser tab — where a web page is handed a file's name and never its path, so it could not tell the backend which file to read. Multi-select imports a whole folder in one go; each file succeeds or fails on its own.

2.2 STEP and IGES need FreeCAD

Those formats are boundary representations, not meshes, and converting one needs a real CAD kernel. If FreeCAD is not installed the studio says so before accepting the file, rather than accepting it and failing silently later. Install FreeCAD with FreeCADCmd on PATH, or set the FREECAD_CMD environment variable, and restart. STL, OBJ and DAE need none of this.

2.3 COLLADA is not measured

A .dae renders, but its volume is not computed: a COLLADA scene graph can nest and transform geometry in ways a simple reader would get wrong, and a wrong volume feeds a wrong mass straight into the dynamics module. Enter that link's mass directly, or supply an STL.

2.4 When a path is refused

Every failure names its own cause rather than a generic "file not found": the folder exists but holds these files instead, that is a directory, that format needs FreeCAD, the file is zero bytes, permission denied, the path is relative and the backend has a different working directory. The format check runs before the existence check, because a .ply that is also mistyped is still a .ply.

3Units and scale

URDF is always metres. CAD is very often millimetres, and nothing in an STL says which.

A bracket exported in millimetres reads as 54 metres across and its volume comes out in the billions of cm³. Each mesh therefore carries its own scale, and a part measuring more than 10 m gets a one-click Treat as millimetres (×0.001). It is never applied silently — guessing wrong shrinks a real gantry by a thousand.

Setting the scale updates every placement of that part at once and is written into the generated URDF as scale="0.001 0.001 0.001". Size and volume are restated in metres as you change it, so the right answer is obvious: 54 × 25 × 38.2 mm, 51.61 cm³.

4Placement — origin and rotation

An assembly exported in one global coordinate system needs an offset on almost every part. Each placement carries a position in metres and a rotation in degrees.

Quarter-turn buttons

X / Y / Z 90° (Shift for −90°). The common CAD fix is one quarter turn — Z-up versus Y-up between packages.

Centre

Offsets the part so its centre of volume sits on the link origin.

Sit on z = 0

Offsets it so its lowest point rests on the floor plane.

Reset

Back to the identity.

Rotations compose properly. Adding 90° to one Euler component is only the same thing as a quarter turn when the other two are zero. Turns are composed as quaternions in the parent frame, so Z 90° followed by X 90° gives rpy (0°, −90°, 90°) — not (90°, 0°, 90°), which is a completely different orientation. Centre and Sit on z = 0 likewise use the bounds as currently rotated, since the usual sequence is square the part up, then sit it down.
URDF's rpy is R = Rz(yaw)·Ry(pitch)·Rx(roll). The preview applies exactly that convention, so what you see is what the file says.

4.1 Where placements live

A placement belongs to a mesh on a link, not to the mesh. The same bracket used twice — mirrored left and right — has two placements that must differ. A mesh not yet assigned to a link carries a default placement instead, which is copied across when you assign it, so a part squared up before assignment stays squared up.

5Links & joints

5.1 Build links from meshes

One click gives every unassigned mesh a link named after its file and chains them together. Run it again and it extends the existing chain rather than branching off the base.

Every joint it creates is fixed, and at the origin. Deliberately. An STL says nothing about where the joints are or which way they turn — that information does not exist in the file — so inventing plausible-looking revolute axes would be fabricating the one thing this studio exists to have you specify. What you get is a valid, complete, visible robot with every part in the tree. Parts stacked on top of each other means the joint origins are still at zero, which is true, and is the thing to go and fix.

5.2 Assignment is many-to-one

One link can take several meshes. A CAD assembly is modelled for manufacture, and a single rigid link is very often a housing, two brackets and a handful of fasteners. A supplier's file might ship thirteen parts for what should be six rigid bodies, so assign each mesh explicitly rather than assuming the CAD structure is the robot structure.

5.3 Joints

Per joint: type (fixed, revolute, continuous, prismatic), parent and child, origin, axis and limits. Axis presets cover the common cases, and a typed vector is normalised for you — a non-unit axis is read differently by different parsers.

5.4 Live preview

The viewport walks the joint tree and applies each joint's origin, so it shows exactly what the generated URDF shows with every joint at zero. The link you are editing lights up blue — clicking a name in the tree tells you which lump of geometry it actually is, which is the hardest thing to work out from a parts list.

6Physical properties

Mass, centre of mass and inertia per link — the data the Torque & Dynamics Studio needs and has no other source for on an imported robot. Entering it here carries it straight through, with no translation step.

Each link can be estimated from its own geometry: a measured mesh volume plus a material density where the mesh is watertight, or the dimensions of a primitive where it is not.

A non-watertight mesh gets no volume. A surface with holes in it encloses no well-defined volume, so no mass can be estimated from a density. The studio reports that instead of returning a plausible-looking number — enter the mass directly, or repair the mesh.

Everything estimated keeps its ESTIMATED badge, and the badge travels into the generated package's README because a URDF has nowhere to record provenance.

This is the loop the six workflows are built around: describe a robot here, size its motors in Torque & Dynamics, check its conditioning in the Jacobian Studio, teach it a path in Motion & Path Planning, and train a network for it in ML for IK — all from one description, with the mass properties and joint limits carried through rather than re-entered.
